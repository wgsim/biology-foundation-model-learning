# 캡스톤 보고서 템플릿

분량은 4~6쪽을 목표로 한다. 모든 숫자는 **노트북 출력에서 코드로 만든 문장**을 옮기고(손으로 옮기다 틀린 사례: 모듈 04·05), 표마다 어느 셀의 출력인지 적는다.

```markdown
# [제목]
- 저자 / 날짜 / 저장소 커밋 / 제안서 버전:

## 요약 (5줄 이내)
질문 · 설정(데이터, 모델, 분할, 시드) · 주 결과(숫자 + 구간) · 결정 규칙의 판정 · 가장 중요한 한계.

## 1. 질문과 사전 등록
제안서의 질문, 주 비교, 결정 규칙을 그대로 붙인다. **제안서에서 바꾼 것**과 이유(결과를 본 뒤였나?).

## 2. 데이터와 출처
- 파일·버전·해시, 모델 리비전, 환경(패키지 버전, 장비), 라이선스 근거 / 미확인 항목.
- 데이터 점검 결과 (중복 제거 수, 결측, 라벨 충돌).

## 3. 분할과 누출 측정
분할별로 **train과의 겹침을 숫자로** 보고한 표. 분할이 막은 경로 / 막지 못한 경로.

## 4. 결과
### 4.1 주 비교 (사전 지정)
| 비교 | Δ [95% 구간] | 이긴 시드 | 판정 |
구간이 무엇에 조건부인지 한 줄.
### 4.2 전체 표 (모든 방법 × 분할, 시드 평균±SD 또는 시드별 값)
### 4.3 민감도 (한 요인씩) — 설정을 고르는 데 쓰지 않았음을 명시
### 4.4 음성 대조와 무작위 초기화 대조

## 5. 해석
- 데이터가 직접 지지하는 것 / 가설 수준인 것 / 말할 수 없는 것.
- 예상과 달랐던 결과와 가능한 원인 2개 이상 (확인했나, 못 했나).
- 단순 baseline이 이긴 경우 그대로 쓴다.

## 6. 한계와 하지 않은 것
- 일반화 한계 (데이터 1개? 모델 크기? 시드 수? 튜닝하지 않은 설정?)
- **실행하지 못한/확인하지 못한 것 목록** (예: 클러스터, 다른 하드웨어, 라이선스, 다른 데이터셋).

## 7. 재현 방법
- 환경 설치, 실행 순서, 소요 시간, 출력 위치. (깨끗한 체크아웃에서 끝까지 도는지 확인했는가?)

## 8. 책임성
- 라이선스, 이중 용도 검토 결과, 공개 범위 결정과 이유.

## 부록
- 변경 기록, 독립 검토 지적과 처리 결과(수용 / 기각 + 근거), provenance.json 요약.
```

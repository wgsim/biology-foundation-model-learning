# 캡스톤 보고서 템플릿

분량은 4~6쪽을 목표로 한다. 모든 숫자는 **노트북 출력에서 코드로 만든 문장**에서 옮기고, 표마다 어느 셀의 출력인지 적는다. 손으로 옮기다 틀린 사례가 모듈 04·05에 있다.

```markdown
# [제목]
- 저자 / 날짜 / 저장소 커밋 / 제안서 버전:

## 요약 (5줄 이내)
다음을 담는다. 질문, 설정(데이터, 모델, 분할, 시드), 주 결과(숫자와 구간), 결정 규칙의 판정, 가장 중요한 한계.

## 1. 질문과 사전 등록
제안서의 질문, 주 비교, 결정 규칙을 그대로 붙인다. **제안서에서 바꾼 것**과 이유를 적고, 그 변경이 결과를 본 뒤였는지도 밝힌다.

## 2. 데이터와 출처
- 파일·버전·해시, 모델 리비전, 환경(패키지 버전, 장비), 라이선스 근거와 미확인 항목을 적는다.
- 데이터 점검 결과(중복 제거 수, 결측, 라벨 충돌)를 적는다.

## 3. 분할과 누출 측정
분할별로 **train과의 겹침을 숫자로** 보고하는 표를 넣는다. 분할이 막은 경로와 막지 못한 경로도 적는다.

## 4. 결과
### 4.1 주 비교 (제안서 커밋 해시: )
| 비교 | Δ 시드 평균 (시드별 값) | 이긴 시드 | 95% 구간 또는 "계산하지 않음: 이유(test 군집 수)" | 판정 |
구간이 있다면 무엇에 조건부인지 한 줄로 적는다. 결정 규칙 함수의 출력은 그대로 옮긴다.
### 4.2 전체 표 (모든 방법 × 분할, 시드 평균±SD 또는 시드별 값)
### 4.3 민감도 (한 요인씩) — 설정을 고르는 데 쓰지 않았음을 명시
### 4.4 음성 진단과 무작위 초기화 대조 (시드마다 새로 만든 초기화)

## 5. 해석
- 데이터가 직접 지지하는 것, 가설 수준인 것, 말할 수 없는 것을 구분해 적는다.
- 예상과 달랐던 결과와 가능한 원인을 2개 이상 적고, 각 원인을 확인했는지 못 했는지 밝힌다.
- 단순 baseline이 이긴 경우 그대로 쓴다.

## 6. 한계와 하지 않은 것
- 일반화 한계를 적는다 (데이터 1개? 모델 크기? 시드 수? 튜닝하지 않은 설정?)
- **실행하지 못한 것과 확인하지 못한 것의 목록**을 적는다 (예: 클러스터, 다른 하드웨어, 라이선스, 다른 데이터셋).

## 7. 재현 방법
- 환경 설치, 실행 순서, 소요 시간, 출력 위치를 적는다. 깨끗한 체크아웃에서 끝까지 도는지 확인했는지도 밝힌다.

## 8. 책임성
- 라이선스, 이중 용도 검토 결과, 공개 범위 결정과 이유를 적는다.

## 부록
- 변경 기록, 독립 검토 지적과 처리 결과(수용 또는 기각과 그 근거), provenance.json 요약을 붙인다.
```

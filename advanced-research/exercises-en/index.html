Exercise 1 — LoRA design space and the parameter-efficiency curve (notebook 01)¶

Change the LoRA rank r ∈ {1, 2, 4, 8, 16, 32}, the target layers (q,v / q,k,v / all linear layers) and the learning rate, and draw the number of trainable parameters vs test Spearman curve (position-block split, 3 or more seeds). Mark the frozen probe and full fine-tuning as reference lines in the same figure.

  • Evaluation criteria: ① the test set was not used to choose the settings (use the validation procedure of exercise 2, or only report the whole curve), ② per-seed values and mean ± standard deviation, ③ a description of the point where the curve saturates and the point where it meets full fine-tuning (if it does not saturate or meet within the observed range, write that), ④ report the training time and the memory cost together, and answer “does LoRA reduce computation, or optimizer memory?”.

Exercise 2 — Making fine-tuning fair with validation-based selection (notebook 01)¶

Notebook 01 fixed the number of epochs and the learning rate in advance. Implement a nested procedure that holds out a validation set from inside the training data in the same way as the outer split (variant level for random, block level for position blocks) and chooses the epochs (early stopping) and the learning rate for each method.

  • Evaluation criteria: ① a check that the validation split never sees the test positions (the position sets do not overlap), ② compare the test Spearman of the fixed setting and the selected setting, paired on the same seeds, ③ the extra computation cost of the selection procedure, ④ describe whether the result changes the conclusion that “fine-tuning beats / does not beat the probe”. If it did not change it, report that too.

  • Advanced (optional): instead of training a randomly initialized head at the same time as the backbone, add a variant that does fine-tuning after first training only the head (LP-FT) or initializes the head with a zero-shot score, and see whether the result changes.

Exercise 3 — Verifying and extending the memory-budget formula (notebook 03)¶

(a) Extend the formula of notebook 03 §2 (full 16P, LoRA 4P + 16P_LoRA) to the 3B and 15B models with the number of parameters confirmed from the model cards (state the source), (b) add an activation term (set up an approximate formula in batch, length and number of layers yourself, and distinguish with and without checkpointing), (c) compare the formula’s prediction with the memory measured on this Mac for ESM-2 35M and 8M.

  • Evaluation criteria: ① state the assumptions of the formula (optimizer, precision), ② prediction vs measurement error and at least 2 hypotheses on the cause of the error, ③ describe that the MPS measurement is not the same quantity as CUDA’s max_memory_allocated, ④ describe, with grounds, from what size single-GPU full fine-tuning becomes impossible (write down the specifications of the GPU you use, after checking).

Exercise 4 — Causal check (intervention) of SAE features (notebook 02)¶

Notebook 02 showed only the feature–keyword correlation. Choose one keyword (e.g., Transmembrane) and one best SAE feature jjj for that keyword (chosen on train only), and remove only that feature’s contribution from the layer-12 residue activation xxx (= the last-layer output, the layer that the logistic probe built on top of it uses as input). To avoid mixing in the reconstruction error, subtract directly from the original activation:

(zjz_jzj​ is the SAE activation computed on the scaled input, and scale is the input normalization coefficient. If you replace it with the reconstruction x^\hat xx^, the loss of the SAE bottleneck, about 20% FVU, comes in with it and cannot be distinguished from the feature-removal effect.) Compare three conditions with the same probe (trained on the original activations): (i) no intervention, (ii) replacing only with the reconstruction x^\hat xx^, (iii) the feature removal by the formula above. As controls, remove in the same way (a) a random SAE feature and (b) the best-on-train one among the original dimensions. The probe is evaluated after pooling, so apply the intervention to the residue activations before pooling.

  • Evaluation criteria: ① the removal target was chosen on train only, ② for a single keyword, report the drop in the AUROC of the test proteins with an interval from the Pfam-group bootstrap, and keep the results extended to several keywords and several features in a separate table, ③ separate and describe the “reconstruction cost” and the “feature-removal effect” by the difference between (ii) and (iii), ④ if the drop is small or absent, describe the possible reasons (information duplicated in other features, superposition, the feature is only correlated with the keyword and the probe does not use it, etc.) and the cases where “there is correlation but no causation” is possible, ⑤ extension (optional): FVU vs the median keyword AUROC for dictionary size {1×, 4×, 8×, 16×} and k ∈ {8, 32, 128}, residue-level activation density, stability across seeds. To do it at layer 6, the intervened activations must be passed again through layers 7–12, and the probe input is layer 12 after that.

Exercise 5 — Benchmark design document (mainly reading, running is optional)¶

Read DOME (Walsh et al. 2021, module 01) and Raji et al. (2021), and write a benchmark design document for 1 protein (or molecule) task of your choice. It should contain (a) the task definition and the source and uncertainty of the labels, (b) the split rule (identity threshold, tools, how to check for leakage; reflecting the lessons of modules 01 and 05), (c) the metrics and how to report uncertainty, (d) the required baselines (including ones that need no training), (e) a check of duplication (contamination) with the pretraining data, (f) version management, license and reproduction procedure, (g) a list of “what cannot be said with the score of this benchmark”.

  • Evaluation criteria: ① a table of which leakage paths the split blocks and which it fails to block, ② the paths by which the score can saturate or overfit, and the mitigations, ③ 3 questions from an imaginary reviewer who rebuts the design document, and the answers, ④ include in the conclusion a sentence that does not generalize the ranking of one benchmark to the actual usefulness of the models.

Exercise 6 — Audit of data/model licenses and research accountability (reading + repository)¶

Set a hypothetical project “release LoRA-fine-tuned ESM-2 weights on some ProteinGym assays”, and, starting from the materials this repository uses (UniProt, ProteinGym, ESM-2, MoleculeNet, ChemBERTa, etc.; the README §7 table), write the following. (a) a license matrix in which you directly checked the license grounds (file, page, API field) of each material, (b) the obligations and constraints when releasing derivatives (LoRA weights, embeddings, tables), (c) a dual-use review reflecting Baker & Church (2024) and Sandbrink (2023) (which functions could be misused, and the options of scope of release, staged access and monitoring).

  • Evaluation criteria: ① mark licenses that could not be checked as “unverified” and state that it is not legal advice, ② compare the grounds of the release decision and the alternatives (no release / restricted release / sharing on request), ③ mark the institution’s policy and whether IRB/IBC applies as items to be checked, ④ a description that neither exaggerates nor underestimates the risk (marking uncertainty with grounds).

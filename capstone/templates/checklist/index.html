제출 전 점검표

이 과정의 모듈 01~06에서 실제로 틀렸거나 틀리기 쉬웠던 것을 모았다. 괄호는 처음 만난 모듈이다. 모든 항목에 예/아니오/해당 없음과 증거(파일·셀)를 적는다.

데이터·출처¶

  • 데이터 파일 해시·버전·릴리스를 기록했다 (UniProt은 릴리스마다 내용이 바뀐다: 05)

  • 모델은 리비전을 고정하고 snapshot_download한 로컬 경로에서 불러왔다 (저장소 ID로 열면 자동 변환 PR 브랜치의 파일이 섞인 적이 있다: 05)

  • 원격 코드(trust_remote_code)는 읽고 고정한 리비전에서만 쓴다. pickle 체크포인트는 weights_only 경로로 읽는다 (05)

  • 접근 승인(gated) 모델·데이터는 사용자가 직접 약관에 동의했다 (05)

  • 라이선스는 **근거(파일·API 필드)**를 적었고, 확인 못 한 것은 "미확인"이라 썼다. 미확인이면 공개·재배포 범위를 제한했다 (06)

  • 같은 서열·분자·텍스트를 분할 전에 병합했다. 라벨 충돌 처리를 적었다 (05: 중복 서열 33개가 train과 test에 걸렸다)

분할¶

  • 분할이 막으려는 누출 경로와 막지 못하는 경로를 적었다 (01, 05)

  • 분할 후 누출을 숫자로 쟀다 (test→train 최근접 유사도, 위치·가족 공유 비율) (05: scaffold 분할에서도 test의 26%가 Tanimoto ≥ 0.7)

  • test의 위치·그룹 수를 확인했다. 이 수는 유효 표본 크기의 대리값이며 행 수가 아니다. 적으면 시드 하나의 변동이 크다 (07 템플릿: test 군집 2개, 음성 진단이 시드마다 ±0.3)

  • 그룹 수가 분할과 내부 CV에 충분하다 (07 템플릿: 길이 55 단백질에서 블록 15는 그룹 4개뿐이었다)

baseline·대조군¶

  • 파라미터를 학습하지 않는 baseline을 포함했다 (최근접 전이, 가장 가까운 train 위치의 평균. train 라벨은 쓰되 train에서만 추정한다) (02, 05, 07)

  • 단순 특징 baseline을 포함했다 (원-핫 · 조성 · 지문 · 기술자 · 작은 기술자 집합) (02, 05)

  • 무작위 초기화 대조군을 시드마다 새로 만들었다 (하나만 쓰면 그 초기화의 운이 결론이 된다) (04, 05, 07)

  • 선택 효과 대조를 넣었다 (수천 후보 중 train 최고를 고르는 절차면 무작위 후보 대조를 쓴다) (06)

  • 음성 대조 (라벨 섞기 · 입력 섞기)는 진단이지 증명이 아니다. 평균이 0 근처인지를 시드 변동과 함께 확인해 보고서에 적고, 벗어나면 원인을 조사한다 (05, 07)

절차¶

  • 표준화·PCA·정규화 선택·특징 선택을 학습 접힘 안에서만 적합했다 (04: PCA가 held-out을 봤다, 06: Ridge 표준화)

  • 설정(층·에폭·LR·임계값)은 사전 고정이거나 검증 분할로 골랐다. 민감도 표는 보고용이다 (04, 06)

  • 표본 추출은 무작위다. 처리 순서(길이순 등)의 앞부분을 쓰지 않았다 (06: PCA 20만 잔기)

  • 시드마다 분할과 초기화가 모두 바뀐다. 같은 시드에서 모든 방법이 같은 train/test를 쓴다 (04)

평가·통계¶

  • 지표의 추정 대상과 계산 규칙을 사전에 정의했다. 예: AUROC는 폴드별로 구해 평균했다 (풀링하면 상수 예측도 0.5에서 벗어난다) (05)

  • 검색 지표는 갤러리 크기와 동점 처리 규칙을 미리 정해 적었다 (정답에 불리한 규칙이 보수적이다) (05: 동점 정의 하나로 최근접 전이 baseline의 R@1이 1.5~2.3배 부풀었다)

  • 비교는 짝지어 했다. 구간은 상관 단위(그룹)의 부트스트랩이며 조건부 구간임을 적었다. test 군집이 충분할 때만 쓴다. 군집이 2~3개면 가능한 재표본이 몇 개뿐이라 구간이 무의미하므로 계산하지 않고 이유를 적는다 (04, 05, 07)

  • 시드가 3개 안팎이면 구간 대신 시드별 값을 보고했다. 같은 데이터를 다시 분할한 시드 반복은 독립 반복이 아니다(test가 겹친다) (06, 07)

  • "중앙값끼리의 차이"와 "차이의 중앙값"을 구분했다 (05, 06)

  • 한 요인씩 바꾼 민감도를 보고했다 (05, 06)

서술¶

  • 보고서의 숫자는 코드가 만든 문장에서 옮겼고, 서술과 실행 출력을 대조했다 (04, 05: 시간·수치 불일치가 반복됐다)

  • 측정 지표가 대리 지표이면 이름과 한계를 적었다 (06: MPS 메모리는 peak가 아니다)

  • 음성·예상 밖 결과를 그대로 썼고, “이 설정에서는”으로 한정했다 (04)

  • 직접 지지 / 가설 / 말할 수 없음을 구분했고, 하지 않은 것 목록이 있다 (04~06)

  • 확인하지 못한 서술에 †를 달았다 (모든 모듈)

재현¶

  • 깨끗한 환경에서 처음부터 끝까지 실행했다. 실행본의 코드 셀이 제출 노트북과 같다 (04~06)

  • 시간을 재는 노트북은 다른 GPU/CPU 작업과 겹치지 않게 돌렸다 (06)

  • 장비·환경 특이점을 기록했다 (06: macOS에서 torchrun은 --local-addr=127.0.0.1이 필요했다)

  • 실패한 실행과 고친 오류를 기록했다 (예: 잘못 적은 리비전 해시를 API와 대조해 바로잡았다: 06)

검토·책임성¶

  • 독립 검토를 받았고(누구에게 무엇을 보냈는지, 검토자 사이에 정보를 공유했는지 기록했다), 각 지적을 코드·출력으로 검증해 수용/기각 근거를 적었다 (05, 06, 07)

  • 이중 용도 검토와 공개 범위 결정을 적었다. 소속 기관 정책 확인이 필요한 항목을 표시했다 (06)

  • 사용자가 승인하지 않은 다운로드·설치를 하지 않았다 (모든 모듈)
